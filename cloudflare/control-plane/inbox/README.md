# StartupBot personal and group inbox

This worker serves the inbox in all 16 StartupBot app languages at its HTTPS origin. It has a dedicated D1 database, email OTP sessions, and static browser assets. On desktop, the sidebar and application menu open chat inside the StartupBot window. The panel loads the configured HTTPS origin in a sandboxed view with a separate persistent session. Use the back link to return to the bot. In the pilot desktop, Settings → Your account uses the same session as Messages. The first verified email OTP creates the account. Later sign-ins reuse its identity, and signing out from Settings also signs out of Messages. The web browser keeps a separate session.

The open inbox uses session-authenticated WebSocket change notifications. The app retrieves content using its regular membership-checked API and polls when the connection is unavailable.

## Use

The operator sets the initial testers in the INBOX_PILOT_EMAILS secret, using a comma-separated list. Invited guests can also sign in. Choose **Tạo cuộc trò chuyện** for a direct conversation or a named group. Opening a direct conversation again returns the existing room, including when both people start the conversation at the same time. A group owner can invite up to 19 other people. Registered recipients see invitations in the inbox. For a new address, the sender can select the invitation language, initially set to their app language and can include a short personal note. The service sends one invitation email per recipient per 24 hours. It includes a link to stop future invitation emails. The guest must verify that same email address within seven days and accept the invitation. A forwarded invitation gives no room access. The selected language applies to the email and its linked invitation screen. The sender writes the personal note in the intended language. The owner sees accepted members. Invite responses are generic, including when the address is unknown, blocked, or at capacity.

Each member sees new posts from the moment they join. A direct chat accepts posts after both people have joined. Every group has the same roles and controls. The owner can appoint or demote administrators, transfer ownership to an active member and close the room. Group administrators can invite by email, rename the group, approve or decline join requests, restrict or restore posting, remove members, ban or unban members and delete member posts. An administrator cannot moderate the owner or another administrator. Members can remove their own posts. In announcement mode only the owner and administrators can send messages or files. A posting restriction survives leaving and rejoining. Bans also prevent rejoining from an invitation.

Registered members see invitations, controls and system labels in their own app language. The web inbox restores the verified account’s language at sign-in. People’s messages, group names, filenames and notes retain their original text.

A group member who can post may invite a bot from their local StartupBot workspace. The selected bot is bound to the verified account. The owner and administrators can remove it. A member starts a discussion by choosing two invited bots and entering a topic. Each bot replies once through its owner's configured provider, with the second receiving the first reply. Both owners keep Messages open on their computers. Each bot can claim up to eight turns in 24 hours. Each user can start up to eight discussions in that period. A round expires after ten minutes. The bot receives the topic and previous bot reply. Its chat history, files and tools are outside this text-only discussion. Model provider usage may incur charges.

Open Conversation info to invite someone by email. The email field is at the top of the panel. A group manager can also create a shareable link valid for seven days. New recipients verify their email, then explicitly request to join. Manager approval is on by default. A manager can allow immediate joining, replace the link or revoke it. Replacing or revoking the link cancels its pending requests. A direct email invitation opens that conversation after sign-in and still requires acceptance. Anyone with a valid group link is eligible to verify an email for the pilot. Members can leave or block future invitations from the owner. Blocking also ends direct messaging with that account. People can unblock an account in **Người đã chặn**.

Markdown files can be sent intact at the normal file limit. On a staged .md or .markdown file, **Chia sẻ dưới dạng skill** sends its UTF-8 text to the open conversation as a skill. The editor accepts up to 8,000 UTF-16 code units, including multibyte text. Other staged files and the current draft are preserved.

**Skill dạng văn bản** and **Bàn giao công việc** use the same Send action as a message. A recipient can save a private copy, download a skill as SKILL.md, or mark a received task complete. Downloading or reading a skill does not install it. The received task belongs to the recipient's inbox. No agent starts and no workspace credentials, files, tools or chat history are shared.

A member can attach a file up to 50 MB (50,000,000 bytes). For Markdown files of at least 2 KiB and other files of at least 128 KiB the app uses lossless gzip during upload when it saves at least 5%. For large multipart uploads the app compares a sample using Brotli and gzip, then compresses off the UI thread when Brotli wins. The file hashes are always over the original data. Compressible consecutive parts can share one request. Files whose sample does not shrink send up to four consecutive parts per request without trying to compress each part. The app sends up to three upload requests at a time. A transient connection failure retries the same request up to twice. Each part is verified against its position and SHA-256 before publication. Retrying a staged upload sends only its missing parts. Quotas and displayed sizes use the original bytes. Each account can upload up to 20 retained files totaling 60 MB per rolling 24 hours. The internal pilot reserves up to 180 MB of raw attachment data in total. Uploads are published after all parts arrive. Uploads up to 1.5 MB that fit in a single request reserve storage and publish in the same database transaction. The daily cleanup reclaims incomplete uploads older than an hour. Downloads require current membership, respect the join boundary and expire with the post. Files download as attachments; the service does not inspect their contents for malware.

Record a voice message from the conversation composer. Stop to preview the clip, remove it, or send it with the same attachment limits. Recording stops after one minute. Members can play and download the clip from the conversation. On a compatible desktop, the separate dictation button uses the workspace's existing speech engine and inserts the words into the draft before sending.

Membership exposes each active member's email address to the other active members. Messages become unreadable through the service after 30 days. A daily scheduled job deletes expired posts. Removing a person or closing a room cannot recall downloads or saved copies. Recipients can delete their saved copies. The service reads plaintext to serve authorized users. It provides no end-to-end encryption.

## Configure a StartupBot environment

Use a StartupBot-controlled Cloudflare account and a verified email sender. The worker needs a D1 database bound as DB and Cloudflare Email Sending bound as EMAIL. The included config names a new database and contains no production IDs. Record the dedicated D1 database ID in the environment's Wrangler configuration. Give that environment its own strong random BETTER_AUTH_SECRET, set BETTER_AUTH_URL to the exact public HTTPS origin without a trailing slash, and set EMAIL_FROM to the verified sender. Restrict the sending binding to that address. Include these runtime variables when deploying the worker and its assets.

From cloudflare/control-plane, use the inbox config for every command. For example, these commands verify packaging and migrate a local database.

```sh
pnpm exec wrangler deploy --dry-run --config inbox/wrangler.jsonc
pnpm exec wrangler d1 migrations apply DB --local --config inbox/wrangler.jsonc
pnpm exec vitest run test/personal-inbox.test.ts
```

For a live environment, apply inbox/migrations to the dedicated remote D1 database, deploy that environment's worker and assets, and verify OTP delivery and revocation with separate consenting test accounts. For the desktop, package the HTTPS origin as extraMetadata.startupbotInboxOrigin, set STARTUPBOT_INBOX_ORIGIN in its launch environment, or set origin in inbox-service.json under its Electron user data directory. Restart the updated app. The menu item lives in the StartupBot menu on macOS and the File menu on Windows and Linux. Unconfigured builds keep the inbox entry hidden.

The inbox uses its own OTP identities. It does not contact any upstream account or relay service. Operators must manage database access, backups and their retention separately.

### Internal desktop organization example

Run `node scripts/testing/organization-email-example.mjs` from the repository root. In StartupBot, open Settings → Account → Organization, choose work sign-in and enter the loopback address printed in the terminal. Use `employee@example.test`. The terminal acts as its test mailbox. Enter the eight-digit code in the same settings panel. Disconnect the demo organization in Settings and stop the terminal process when finished.

The example keeps one enrollment in memory and grants no model access. A managed portal that advertises `capabilities.desktopEmailOtp` must verify membership and bind the emailed challenge to the pending device before approving enrollment. Portals that support browser approval continue to use their existing flow.
