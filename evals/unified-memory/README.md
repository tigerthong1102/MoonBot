# Semantic recall evaluation scaffold

`cases.json` contains 96 separately authored synthetic question pairs (48 development and 48 held-out), version 2. There are positive paraphrases and negatives involving actions, conditions, subjects, status, quantity, scope, and negation; the held-out set includes Vietnamese and cross-language questions. Cases have one saved question each. Each outcome says whether that saved answer may be reused for the query. The wording is fictional and contains no customer data. These labels are design judgments, not validated user outcomes. Some development ideas overlap examples in the production prompt; do not treat development as independent model assessment.

The held-out cases are separate from development but publicly readable here. This is a regression split, not a secret blind test. No model should be tuned against held-out labels; any credible generalization result needs a larger independently authored blind corpus and manual label review. This scaffold has **96, not 200, distinct cases** and is not evidence that the requested 200-case benchmark is complete.

An independent code-review agent reviewed version 2 for ambiguity and overlap; seven pairs were reworded in response. A pair does not include a concrete policy answer, so even a plausible semantic label is not proof that the same answer is correct under every business policy. An additional domain reviewer and answer-grounded dataset are needed before treating these labels as gold.

`context-cases.json` is a separate preliminary set of 260 hand-authored synthetic cases, with 133 development and 127 held-out. Each records a fictional scenario, the saved question and synthetic answer, a new query, and a rationale for the proposed label. The answer is a test fixture, not a real owner's approval. A domain reviewer has not validated the labels. Related intents recur across the two public corpora, so the held-out set is not blind. Do not combine its 260 cases with the 96 question-only cases as if all 356 had the same evidence quality. The answer-grounded set has 204 additional cases beyond the original 56. The preceding 32 additions received independent label review; all labels remain synthetic judgments rather than domain-validated outcomes. Three development rows cover two scenarios: answer-dependent one-versus-two order cancellation in word and digit variants, and equivalent number notation for a delivery fee. The cancellation variants are not independent scenarios, and the row count does not establish the number of independent cases. They do not establish model performance. The current digit prefilter can reject the two digit-containing examples even when the supplied synthetic answer supports reuse. The current grounded development split has 54 match and 79 none; held-out has 48 match and 79 none. A constant `none` predictor would score 158/260 overall without retrieving anything. The additions were selected partly to increase matches and language coverage; many are short direct paraphrases, so the class balance is artificial and the corpus is not representative of production or a substitute for adversarial evaluation. The saved questions remain predominantly English in development and Vietnamese in held-out despite additions in both languages, so split and language remain confounded; report per-language and per-class performance and do not treat this public split as independent generalization evidence.

An isolated adapter executes the actual `createAiTwinPreview().recall` with a fixed in-process fake writer and synthetic lessons, whose writer contains no network or credential operations. This is an in-process fixture, not an OS-enforced network sandbox. It supports explicit `same`, `none`, and `error` fake modes; these are deliberately scripted responses, not semantic predictions. The recall number/negation prefilters and verification still execute. Output is a corpus-bound envelope with the commit, dirty status, selected source and adapter hashes, call count, zero fake cost, timestamp, and a `deterministic-fake` provenance declaration. It never passes the fixture answer or context to the provider. Run it only against these fictional corpus files, redirecting output to a temporary path if needed:

```sh
node --experimental-strip-types evals/unified-memory/fake-recall-run.ts --context --fake=same > /tmp/twin-fake.json
node --experimental-strip-types evals/unified-memory/report.ts --context /tmp/twin-fake.json
```

The report identifies such an envelope as `DECLARED_SYNTHETIC_FAKE_NOT_MODEL`. This label is self-declared, not a provenance attestation. Hashes cover the preview, redactor, adapter and runner files only; dirty status does not preserve a diff, and transitive dependencies and runtime are not captured. These results validate wiring and recall guard behavior only; they do not measure model quality, production compatibility, live providers or actual cost. No real provider adapter is configured by this command. A real-provider run requires a separate, explicitly authorized integration with provider-specific limits, accounting, credential handling and verified collection provenance.

Both report commands report **NOT RUN** for every cell. They never contact a provider and need no credentials. The tests exercise score accounting and fixture structure, not semantic behavior. There is no baseline semantic score in this branch.

For a future independently authorized evaluation, an adapter must execute the actual `createAiTwinPreview().recall` implementation against the saved question and query with a real configured provider, record provider/model/commit and cost outside this corpus, and save results in an envelope `{ "corpusVersion": 2, "corpusSha256": "<exact corpus SHA-256>", "predictions": [{ "id": "hold-01", "result": "match" | "none" | "error" }] }`. Obtain the exact corpus version and SHA-256 from the report before collecting results, and preserve them with provider/model/commit and cost metadata. Any byte change, even whitespace, changes the digest and requires a fresh collection. An error includes timeouts and unavailable providers; it must not be replaced with `none`. The fake adapter below does not implement this real-provider evaluation or authorize network usage. Score a separately obtained result file with:

```sh
node --experimental-strip-types evals/unified-memory/report.ts /path/to/results.json
node --experimental-strip-types evals/unified-memory/report.ts --context /path/to/context-results.json
```

Output groups by split and category and records positive and negative denominators, attempts, errors, correct decisions, false matches, and false misses. Missing cases yield INCOMPLETE, not a perfect score. Mismatched version or exact-byte digest, unbound legacy arrays, unknown IDs and duplicate IDs are rejected. Report false matches and false misses separately; for a complete run with no errors, false-match rate is false matches divided by negative cases, and false-miss rate is false misses divided by positive cases. Errors and incomplete runs must be reported instead of silently excluded. Never treat imported results as verified evidence unless their collection method is independently established.

This scaffold does not evaluate security, source authorization, cross-tenant leakage, consent, automatic learning, cost ceilings, realistic multi-candidate retrieval, prompt injection resistance, memory lifecycle, UI or production availability. The separate AgenticOS lifecycle suite remains at `evals/ai-twin/agenticos-memory.test.ts`. Those properties require separate isolated, end-to-end tests and should not be inferred from this corpus or its scorer.

In the current product, semantic recall compares the query to saved **questions**; it does not send the saved answer or fixture context to its matching prompt. `match` means the saved answer supplies sufficient evidence to formulate an answer to the query; it does not mean the answer can always be copied verbatim. Cases in the `answer-dependent` category need the saved answer, including when a query reverses polarity or narrows a broader answer; score them separately, since question-only matching cannot establish answer sufficiency. The contextual answers here justify the labels for reviewers; an adapter must not silently inject these answers into that prompt and claim to evaluate the same implementation.
