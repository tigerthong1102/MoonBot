# 路線圖更新

> 使用工作區為下面指定的資料來源配置的連接器。如果連接器不可用，請要求匯出。

更新、建立產品路線圖或重新確定產品路線圖的優先順序。

## 用途

```
/roadmap-update $ARGUMENTS
```

## 工作流程

### 1.了解現狀

如果**~~項目追蹤器**已連線：
- 提取目前路線圖項目及其狀態、受讓人和日期
- 識別逾期、有風險或最近完成的項目
- 展示任何沒有明確所有者或日期的物品

如果沒有連接專案管理工具：
- 要求用戶描述他們當前的路線圖或貼上/上傳它
- 接受任何格式：清單、表格、電子表格、螢幕截圖或散文描述

### 2. 確定操作

詢問用戶想做什麼：

**新增項目**：路線圖中的新功能、計劃或工作項目
- 收集：名稱、描述、優先順序、估計工作量、目標時間範圍、所有者、依賴關係
- 根據目前的優先事項和能力提出適合的建議

**更新狀態**：變更現有項目的狀態
- 選項：未開始、進行中、有風險、已封鎖、已完成、切斷
- 對於「有風險」或「被阻止」：詢問阻止者和緩解計劃

**重新確定優先順序**：更改項目的順序或優先級
- 詢問發生了什麼變化（新資訊、策略轉變、資源變化、客戶回饋）
- 如果有幫助，請應用優先框架 - 請參閱下面的 **優先框架**，以了解 RICE、MoSCoW、ICE 和價值與努力
- 顯示之前/之後的比較

**移動時間軸**：移動項目的日期
- 詢問原因（範圍變更、依賴性滑動、資源限制）
- 確定對相關項目的下游影響
- 標記超出嚴格期限的項目

**建立新路線圖**：從頭開始建立路線圖
- 詢問時間範圍（季度、半年、年）
- 詢問格式偏好（現在/下一步/稍後、季度專欄、OKR 對齊）- 請參閱下面的 **路線圖框架**
- 收集要包含的舉措清單

### 3. 產生路線圖摘要

使用以下命令產生路線圖視圖：

#### 狀態概覽
快速摘要：X 項正在進行中，Y 項在此期間完成，Z 項處於風險中。

#### 路線圖項目
對於每個項目，顯示：
- 名稱和一行描述
- 狀態指示燈（正常/有風險/受阻/已完成/未開始）
- 目標時間範圍或日期
- 業主
- 關鍵依賴項

項目分組依據：
- 時間範圍（現在/下一個/稍後）或季度，取決於格式
- 或如果使用者願意的話可以按主題/目標

#### 風險和依賴性
- 被阻止或有風險的項目，以及詳細信息
- 跨團隊依賴及其狀態
- 接近嚴格期限的項目

#### 本次更新的變更
如果這是現有路線圖的更新，請總結更改的內容：
- 新增、刪除或重新調整優先順序的項目
- 時間軸轉變
- 狀態變化

### 4. 跟進

產生路線圖後：
- 提供針對特定受眾的格式（執行摘要、工程細節、面對客戶）
- 提議起草有關路線圖變更的通訊
- 如果專案管理工具已連接，則提供更新票證狀態

## 路線圖框架

### 現在/下一步/稍後
最簡單且通常最有效的路線圖格式：

- **現在**（當前衝刺/月）：致力於工作。對範圍和時間表充滿信心。這些是團隊正在積極建立的東西。
- **下一步**（未來 1-3 個月）：計劃的工作。對什麼有足夠的信心，但對具體的時間缺乏信心。範圍和優先級但尚未開始。
- **後來**（3-6個月以上）：定向。這些是我們打算追求的策略賭注和機會，但範圍和時間安排是靈活的。

何時使用：大多數團隊，大多數時間。特別適合與外部或與領導層溝通，因為它可以避免日期的錯誤精確性。

### 季主題
每季圍繞 2-3 個主題組織路線圖：

- 每個主題代表一個策略投資領域（例如「企業準備」、「啟動改進」、「平台可擴展性」）
- 在每個主題下，列出計劃的具體舉措
- 主題應與公司或團隊 OKR 相匹配
- 這種格式可以很容易地解釋為什麼你正在建立你正在建立的東西

何時使用：當您需要表現出策略一致性時。適合規劃會議和高階主管溝通。

### OKR 一致路線圖
將路線圖專案直接對應到目標和關鍵結果：

- 從該期間團隊的 OKR 開始
- 在每個關鍵結果下，列出將推動該指標的舉措
- 包括每項措施對關鍵結果的預期影響
- 這在您建立的內容和您衡量的內容之間建立了明確的責任

何時使用：基於 OKR 的組織。有助於確保每項措施都有明確的「原因」並與可衡量的結果相關聯。

### 時間軸/甘特圖視圖
基於日曆的視圖，其中的項目位於時間軸上：

- 顯示開始日期、結束日期和持續時間
- 可視化並行性和順序
- 適合識別資源衝突
- 顯示項目之間的依賴關係

何時使用：與工程一起執行計劃。辨識日程衝突。不利於外部溝通（產生錯誤的精確期望）。

## 優先順序框架

### 稻米分數
從四個維度對每個舉措進行評分，然後計算 RICE =（覆蓋範圍 x 影響力 x 置信度）/努力程度

- **覆蓋範圍**：在給定時間段內這將影響多少用戶/客戶？使用具體數字（例如「每季 500 個使用者」）。
- **影響**：這會對每個接觸到的人產生多大的影響？評分標準：3 = 大量、2 = 高、1 = 中、0.5 = 低、0.25 = 最小。
- **信心**：我們對影響範圍和影響的估計有多大信心？ 100% = 高置信度（有數據支持），80% = 中置信度（一些證據），50% = 低置信度（直覺）。
- **努力**：多少人月的工作？包括工程、設計和任何其他職能。

何時使用：當您需要定量、合理的優先順序時。適合比較大量積壓的計畫。對於難以估計影響的策略賭注不太有利。

### 莫斯科
將項目分類為必須有、應該有、可以有、不會有：

- **必須具備**：沒有這些，路線圖就是失敗的。不可協商的承諾。
- **應該有**：重要且符合預期，但沒有它們交付也是可行的。
- **可能有**：理想但優先順序明顯較低。僅在容量允許的情況下包括。
- **不會**：明確超出此期間的範圍。為了清晰起見，列出來很重要。

何時使用：確定版本或季度的範圍。與利害關係人就合適的事項進行談判。適合強制對話優先順序。

### ICE分數
比米飯簡單。在三個維度上對每個項目進行 1-10 分評分：

- **影響**：這將使目標指標發生多大變化？
- **信心**：我們對影響估計的信心有多大？
- **輕鬆**：實施起來有多容易？ （努力的倒數 — 更高=更容易）

ICE 分數 = 影響力 x 信心 x 輕鬆度

何時使用：快速確定待辦事項的功能優先順序。適合早期產品或當您沒有足夠的 RICE 資料時。

### 價值與努力矩陣
在 2x2 矩陣上繪製舉措：

- **高價值，低投入**（快速獲勝）：首先執行這些操作。
- **高價值，高努力**（大賭注）：仔細計劃這些。值得投資，但需要適當的範圍界定。
- **低價值，低努力**（填充）：當您有閒置能力時執行這些操作。
- **低價值，高努力**（錢坑）：不要做這些。從待辦事項中刪除。

何時使用：團隊規劃會議中的視覺優先順序。有利於建立對權衡的共同理解。

## 依賴關係映射

### 識別依賴關係
尋找這些類別之間的依賴關係：

- **技術依賴性**：功能 B 需要功能 A 的基礎設施工作
- **團隊依賴性**：功能需要另一個團隊的工作（設計、平台、數據）
- **外部依賴**：等待供應商、合作夥伴或第三方集成
- **知識依賴性**：開始之前需要研究或調查結果
- **順序依賴**：必須在啟動功能 B 之前發布功能 A（共享程式碼、使用者流程）

### 管理依賴關係
- 在路線圖中明確列出所有依賴項
- 為每個依賴項分配一個所有者（誰負責解決它）
- 設定“需要”日期：依賴項何時需要解決此問題
- 圍繞依賴關係建立緩衝區——它們是任何路線圖上風險最高的項目
- 儘早標記跨越團隊邊界的依賴關係 - 這些需要協調
- 制定應急計畫：如果依賴關係消失怎麼辦？

### 減少依賴
- 你能建立一個更簡單的版本來避免依賴嗎？
- 您可以使用介面契約或模擬來並行化嗎？
- 您可以以不同的順序來更早地移動依賴項嗎？
- 您能否將工作吸收到您的團隊中以消除跨團隊的協調？

## 容量規劃

### 估計容量
- 從工程師的數量和時間段開始
- 減去已知開銷：會議、值班輪值、面試、假期、PTO
- 一個常見的經驗法則：工程師將 60-70% 的時間花在計畫的功能工作上
- 考慮新成員的團隊成長時間

### 分配容量
對於大多數產品團隊來說，健康的分配：

- **70% 計畫功能**：推進策略目標的路線圖項目
- **20% 技術健康**：技術債、可靠性、性能、開發人員體驗
- **10% 計劃外**：緊急問題、快速獲勝和其他團隊請求的緩衝

根據團隊背景調整比率：
- 新產品：更多功能工作，更少技術債務
- 成熟的產品：更多的技術債和可靠性投資
- 事件後：可靠性更高，功能更少
- 快速成長：更高的可擴展性和效能

### 能力與野心
- 如果路線圖承諾超出了能力，則必須給予某些東西
- 不要透過假裝人們可以做得更多來解決能力問題——透過縮小範圍來解決
- 當您添加到路線圖時，請始終詢問：“結果如何？”
- 承諾更少的事情並可靠地交付比過度承諾並令人失望更好

## 溝通路線圖變更

### 當路線圖改變時
路線圖變更的常見觸發因素：
- 領導階層新的策略重點
- 改變優先順序的客戶回饋或研究
- 改變估計的技術發現
- 來自另一個團隊的依賴單
- 資源變化（團隊擴大或縮小，關鍵人員離開）
- 需要回應的競爭舉措

### 如何溝通變更
1. **承認變化**：直接了解正在發生的變化以及原因
2. **解釋原因**：哪些新資訊推動了這個決定？
3. **顯示權衡**：為了騰出空間而降低了哪些優先權？或什麼是滑倒？
4. **顯示新計劃**：更新了路線圖並反映了變化
5. **承認影響**：誰受到影響以及如何受到影響？期望取消優先順序的專案的利害關係人需要直接聽到它。

### 避免路線圖鞭打
- 不要為每一條新資訊更改路線圖。改變要有一個門檻。
- 除非確實緊急，否則按自然節奏（每月、每季）批量更新路線圖。
- 區分「路線圖變更」（策略重新調整優先順序）和「範圍調整」（正常執行細化）。
- 追蹤路線圖更改的頻率。頻繁的變化可能意味著策略不明確，而不是良好的回應能力。

## 輸出格式

使用清晰、可掃描的格式。表格非常適合路線圖專案。使用文字狀態標籤：**完成**、**正常**、**有風險**、**已封鎖**、**未開始**。

## 溫馨提示

- 路線圖是一種溝通工具，而不是專案計畫。保持正確的高度－主題和結果，而不是任務。
- 重新確定優先順序時，一定要詢問發生了什麼變化。優先順序的轉變應該由新資訊驅動，而不是突發奇想。
- 及早標記容量問題。如果路線圖的工作量超出了團隊的處理能力，請說出來。
- 依賴性是路線圖面臨的最大風險。明確地呈現它們。
- 如果用戶要求添加某些東西，請務必詢問哪些內容會脫落或移動。路線圖與容量的關係是零和遊戲。
