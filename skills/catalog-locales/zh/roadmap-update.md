# 路线图更新

> 使用工作区为下面指定的数据源配置的连接器。如果连接器不可用，请请求导出。

更新、创建产品路线图或重新确定产品路线图的优先级。

## 用途

```
/roadmap-update $ARGUMENTS
```

## 工作流程

### 1.了解现状

如果**~~项目跟踪器**已连接：
- 提取当前路线图项目及其状态、受让人和日期
- 识别逾期、有风险或最近完成的项目
- 展示任何没有明确所有者或日期的物品

如果没有连接项目管理工具：
- 要求用户描述他们当前的路线图或粘贴/上传它
- 接受任何格式：列表、表格、电子表格、屏幕截图或散文描述

### 2. 确定操作

询问用户想做什么：

**添加项目**：路线图中的新功能、计划或工作项目
- 收集：名称、描述、优先级、估计工作量、目标时间范围、所有者、依赖关系
- 根据当前的优先事项和能力提出适合的建议

**更新状态**：更改现有项目的状态
- 选项：未开始、进行中、有风险、已阻止、已完成、切断
- 对于“有风险”或“被阻止”：询问阻止者和缓解计划

**重新确定优先级**：更改项目的顺序或优先级
- 询问发生了什么变化（新信息、策略转变、资源变化、客户反馈）
- 如果有帮助，请应用优先级框架 - 请参阅下面的 **优先级框架**，了解 RICE、MoSCoW、ICE 和价值与努力
- 显示之前/之后的比较

**移动时间线**：移动项目的日期
- 询问原因（范围变更、依赖性滑动、资源限制）
- 确定对相关项目的下游影响
- 标记超出严格期限的项目

**创建新路线图**：从头开始构建路线图
- 询问时间范围（季度、半年、年）
- 询问格式偏好（现在/下一步/稍后、季度专栏、OKR 对齐）- 请参阅下面的 **路线图框架**
- 收集要包括的举措清单

### 3. 生成路线图摘要

使用以下命令生成路线图视图：

#### 状态概览
快速摘要：X 项正在进行中，Y 项在此期间完成，Z 项处于风险中。

#### 路线图项目
对于每个项目，显示：
- 名称和一行描述
- 状态指示器（正常/有风险/受阻/已完成/未开始）
- 目标时间范围或日期
- 业主
- 关键依赖项

项目分组依据：
- 时间范围（现在/下一个/稍后）或季度，取决于格式
- 或者如果用户愿意的话可以按主题/目标

#### 风险和依赖性
- 被阻止或有风险的项目，以及详细信息
- 跨团队依赖及其状态
- 接近严格期限的项目

#### 本次更新的变更
如果这是对现有路线图的更新，请总结更改的内容：
- 添加、删除或重新调整优先级的项目
- 时间线转变
- 状态变化

### 4. 跟进

生成路线图后：
- 提供针对特定受众的格式（执行摘要、工程细节、面向客户）
- 提议起草有关路线图变更的通讯
- 如果项目管理工具已连接，则提供更新票证状态

## 路线图框架

### 现在/下一步/稍后
最简单且通常最有效的路线图格式：

- **现在**（当前冲刺/月）：致力于工作。对范围和时间表充满信心。这些是团队正在积极建设的东西。
- **下一步**（未来 1-3 个月）：计划的工作。对什么有足够的信心，但对具体的时间缺乏信心。范围和优先级但尚未开始。
- **后来**（3-6个月以上）：定向。这些是我们打算追求的战略赌注和机会，但范围和时间安排是灵活的。

何时使用：大多数团队，大多数时间。特别适合与外部或与领导层沟通，因为它可以避免日期的错误精确性。

### 季度主题
每季度围绕 2-3 个主题组织路线图：

- 每个主题代表一个战略投资领域（例如“企业准备情况”、“激活改进”、“平台可扩展性”）
- 在每个主题下，列出计划的具体举措
- 主题应与公司或团队 OKR 相匹配
- 这种格式可以很容易地解释为什么你正在构建你正在构建的东西

何时使用：当您需要表现出战略一致性时。适合规划会议和高管沟通。

### OKR 一致路线图
将路线图项目直接映射到目标和关键结果：

- 从该期间团队的 OKR 开始
- 在每个关键结果下，列出将推动该指标的举措
- 包括每项举措对关键结果的预期影响
- 这在您构建的内容和您衡量的内容之间建立了明确的责任

何时使用：基于 OKR 的组织。有助于确保每项举措都有明确的“原因”并与可衡量的结果相关联。

### 时间轴/甘特图视图
基于日历的视图，其中的项目位于时间轴上：

- 显示开始日期、结束日期和持续时间
- 可视化并行性和顺序
- 适合识别资源冲突
- 显示项目之间的依赖关系

何时使用：与工程一起执行计划。识别日程安排冲突。不利于外部沟通（产生错误的精确期望）。

## 优先顺序框架

### 稻米分数
从四个维度对每个举措进行评分，然后计算 RICE =（覆盖范围 x 影响力 x 置信度）/努力程度

- **覆盖范围**：在给定时间段内这将影响多少用户/客户？使用具体数字（例如“每季度 500 个用户”）。
- **影响**：这会对每个接触到的人产生多大的影响？评分标准：3 = 大量、2 = 高、1 = 中等、0.5 = 低、0.25 = 最小。
- **信心**：我们对影响范围和影响的估计有多大信心？ 100% = 高置信度（有数据支持），80% = 中置信度（一些证据），50% = 低置信度（直觉）。
- **努力**：多少人月的工作？包括工程、设计和任何其他职能。

何时使用：当您需要定量、合理的优先级时。适合比较大量积压的计划。对于难以估计影响的战略赌注不太有利。

### 莫斯科
将项目分类为必须有、应该有、可以有、不会有：

- **必须具备**：没有这些，路线图就是失败的。不可协商的承诺。
- **应该有**：重要且符合预期，但没有它们交付也是可行的。
- **可能有**：理想但优先级明显较低。仅在容量允许的情况下包括。
- **不会**：明确超出此期间的范围。为了清晰起见，列出来很重要。

何时使用：确定版本或季度的范围。与利益相关者就合适的事项进行谈判。适合强制对话优先级。

### ICE分数
比米饭简单。在三个维度上对每个项目进行 1-10 分评分：

- **影响**：这将使目标指标发生多大变化？
- **信心**：我们对影响估计的信心有多大？
- **轻松**：实施起来有多容易？ （努力的倒数 — 更高=更容易）

ICE 分数 = 影响力 x 信心 x 轻松度

何时使用：快速确定待办事项的功能优先级。适合早期产品或当您没有足够的 RICE 数据时。

### 价值与努力矩阵
在 2x2 矩阵上绘制举措：

- **高价值，低投入**（快速获胜）：首先执行这些操作。
- **高价值，高努力**（大赌注）：仔细计划这些。值得投资，但需要适当的范围界定。
- **低价值，低努力**（填充）：当您有闲置能力时执行这些操作。
- **低价值，高努力**（钱坑）：不要做这些。从待办事项中删除。

何时使用：团队规划会议中的视觉优先级。有利于建立对权衡的共同理解。

## 依赖关系映射

### 识别依赖关系
寻找这些类别之间的依赖关系：

- **技术依赖性**：功能 B 需要功能 A 的基础设施工作
- **团队依赖性**：功能需要另一个团队的工作（设计、平台、数据）
- **外部依赖**：等待供应商、合作伙伴或第三方集成
- **知识依赖性**：开始之前需要研究或调查结果
- **顺序依赖**：必须在启动功能 B 之前发布功能 A（共享代码、用户流程）

### 管理依赖关系
- 在路线图中明确列出所有依赖项
- 为每个依赖项分配一个所有者（谁负责解决它）
- 设置“需要”日期：依赖项何时需要解决此问题
- 围绕依赖关系建立缓冲区——它们是任何路线图上风险最高的项目
- 尽早标记跨越团队边界的依赖关系 - 这些需要协调
- 制定应急计划：如果依赖关系消失怎么办？

### 减少依赖
- 你能构建一个更简单的版本来避免依赖吗？
- 您可以使用接口契约或模拟来并行化吗？
- 您可以以不同的顺序来更早地移动依赖项吗？
- 您能否将工作吸收到您的团队中以消除跨团队的协调？

## 容量规划

### 估计容量
- 从工程师的数量和时间段开始
- 减去已知开销：会议、值班轮换、面试、假期、PTO
- 一个常见的经验法则：工程师将 60-70% 的时间花在计划的功能工作上
- 考虑新成员的团队成长时间

### 分配容量
对于大多数产品团队来说，健康的分配：

- **70% 计划功能**：推进战略目标的路线图项目
- **20% 技术健康度**：技术债务、可靠性、性能、开发人员体验
- **10% 计划外**：紧急问题、快速获胜和其他团队请求的缓冲

根据团队背景调整比率：
- 新产品：更多功能工作，更少技术债务
- 成熟的产品：更多的技术债务和可靠性投资
- 事件后：可靠性更高，功能更少
- 快速增长：更高的可扩展性和性能

### 能力与野心
- 如果路线图承诺超出了能力，则必须给予某些东西
- 不要通过假装人们可以做得更多来解决能力问题——通过缩小范围来解决
- 添加到路线图时，请始终询问：“结果如何？”
- 承诺更少的事情并可靠地交付比过度承诺并令人失望更好

## 沟通路线图变更

### 当路线图改变时
路线图变更的常见触发因素：
- 领导层新的战略重点
- 改变优先级的客户反馈或研究
- 改变估计的技术发现
- 来自另一个团队的依赖单
- 资源变化（团队扩大或缩小，关键人员离开）
- 需要响应的竞争举措

### 如何沟通变更
1. **承认变化**：直接了解正在发生的变化以及原因
2. **解释原因**：哪些新信息推动了这一决定？
3. **显示权衡**：为了腾出空间而降低了哪些优先级？或者什么是滑倒？
4. **显示新计划**：更新了路线图并反映了变化
5. **承认影响**：谁受到影响以及如何受到影响？期望取消优先级的项目的利益相关者需要直接听到它。

### 避免路线图鞭打
- 不要为每一条新信息更改路线图。改变要有一个门槛。
- 除非确实紧急，否则按自然节奏（每月、每季度）批量更新路线图。
- 区分“路线图变更”（战略重新调整优先级）和“范围调整”（正常执行细化）。
- 跟踪路线图更改的频率。频繁的变化可能意味着策略不明确，而不是良好的响应能力。

## 输出格式

使用清晰、可扫描的格式。表格非常适合路线图项目。使用文本状态标签：**完成**、**正常**、**有风险**、**已阻止**、**未开始**。

## 温馨提示

- 路线图是一种沟通工具，而不是项目计划。保持正确的高度——主题和结果，而不是任务。
- 重新确定优先级时，一定要询问发生了什么变化。优先级的转变应该由新信息驱动，而不是突发奇想。
- 及早标记容量问题。如果路线图的工作量超出了团队的处理能力，请说出来。
- 依赖性是路线图面临的最大风险。明确地呈现它们。
- 如果用户要求添加某些东西，请务必询问哪些内容会脱落或移动。路线图与容量的关系是零和游戏。
