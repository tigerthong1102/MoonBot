# 写规范

> 使用工作区为下面指定的数据源配置的连接器。如果连接器不可用，请请求导出。

编写功能规范或产品需求文档 (PRD)。

## 用途

## 工作流程

### 1.了解功能

询问用户他们想要什么规格。接受以下任何一项：
- 功能名称（“SSO 支持”）
- 问题陈述（“企业客户不断要求集中身份验证”）
- 用户请求（“用户希望将数据导出为 CSV”）
- 一个模糊的想法（“我们应该对入职下降采取一些措施”）

### 2. 收集背景信息

询问用户以下信息。保持对话——不要一次性抛出所有问题。首先询问最重要的问题，然后填补空白：

- **用户问题**：这解决了什么问题？谁经历过？
- **目标用户**：服务于哪些用户群？
- **成功指标**：我们如何知道这是否有效？
- **限制**：技术限制、时间表、监管要求、依赖性
- **现有技术**：以前是否尝试过？有现成的解决方案吗？

### 3. 从连接的工具中提取上下文

如果**~~项目跟踪器**已连接：
- 搜索相关门票、史诗或功能
- 引入任何现有的要求或验收标准
- 确定对其他工作项的依赖关系

如果**~~知识库**已连接：
- 搜索相关研究文档、先前规格或设计文档
- 提取相关的用户研究结果
- 查找相关会议记录或决策记录

如果**~~design**已连接：
- 提取相关的模型、线框图或设计探索
- 搜索与该功能相关的设计系统组件

如果这些工具未连接，则完全根据用户提供的内容进行工作。不要要求用户连接工具——只需继续使用可用信息。

### 4. 生成PRD

使用这些部分生成结构化 PRD。请参阅下面的 **PRD 结构**，了解每个部分应包含的内容的详细指导。

- **问题陈述**：用户问题、受影响的人以及不解决的影响（2-3句话）
- **目标**：与用户或业务指标相关的 3-5 个具体的、可衡量的结果
- **非目标**：明确超出范围的 3-5 件事，每件事都有简要的理由
- **用户故事**：标准格式（“作为[用户类型]，我想要[能力]以便[利益]”），按角色分组
- **要求**：分为必备条件 (P0)、必备条件 (P1) 和未来考虑因素 (P2)，每项都有验收标准
- **成功指标**：领先指标（快速变化）和滞后指标（随时间变化），以及具体目标
- **开放问题**：未解决的问题，标记为需要回答的人（工程、设计、法律、数据）
- **时间表注意事项**：严格的截止日期、依赖性和阶段性

### 5. 回顾和迭代

生成PRD后：
- 询问用户是否有任何部分需要调整
- 提议扩展特定部分
- 提供创建后续工件（设计概要、工程单细目、利益相关者推介）

## 珠三角结构

### 问题陈述
- 用2-3句话描述用户问题
- 谁遇到过这个问题以及出现的频率
- 不解决这个问题的成本是什么（用户痛苦、业务影响、竞争风险）
- 将此作为证据：用户研究、支持数据、指标或客户反馈

### 目标
- 此功能应实现 3-5 个具体的、可衡量的结果
- 每个目标都应该回答：“我们如何知道这个成功了？”
- 区分用户目标（用户得到什么）和业务目标（公司得到什么）
- 目标应该是结果，而不是输出（“将实现第一个值的时间减少 50%”而不是“构建入门向导”）

### 非目标
- 此功能明确不会执行 3-5 件事
- 超出此版本范围的相邻功能
- 对于每个非目标，简要解释为什么它超出范围（影响不够、太复杂、单独的倡议、不成熟）
- 非目标可防止实施过程中的范围蔓延，并与利益相关者设定期望

### 用户故事
以标准格式编写用户故事：“作为[用户类型]，我想要[能力]以便[利益]”

指南：
- 用户类型应该足够具体且有意义（“企业管理员”而不仅仅是“用户”）
- 该能力应该描述他们想要完成什么，而不是如何完成
- 好处应该解释“为什么”——这能带来什么价值
- 包括边缘情况：错误状态、空状态、边界条件
- 如果该功能服务于多个角色，则包括不同的用户类型
- 按优先级排序——最重要的故事优先

示例：
- “作为团队管理员，我想为我的组织配置 SSO，以便我的团队成员可以使用他们的公司凭据登录”
- “作为团队成员，我希望自动重定向到我公司的 SSO 登录，这样我就不需要记住单独的密码”
- “作为团队管理员，我想查看哪些成员已通过 SSO 登录，以便我可以验证部署是否正常”

### 要求

**必备 (P0)**：如果没有这些，该功能就无法发货。这些代表了该功能的最低可行版本。问：“如果我们删掉这个，这个功能还能解决核心问题吗？”如果不是，则为P0。

**锦上添花 (P1)**：显着改善体验，但核心用例无需它们即可工作。这些通常会在发布后快速跟进。

**未来的考虑因素 (P2)**：明显超出了 v1 的范围，但我们希望以稍后支持它们的方式进行设计。记录这些可以防止意外的架构决策，以免日后变得困难。

对于每个要求：
- 对预期行为进行清晰、明确的描述
- 包括验收标准（见下文）
- 注意任何技术考虑因素或限制
- 标记对其他团队或系统的依赖关系

### 开放性问题
- 实施前或实施过程中需要回答的问题
- 标记每个人应该回答（工程、设计、法律、数据、利益相关者）
- 区分阻塞问题（开始前必须回答）和非阻塞问题（可以在实施过程中解决）

### 时间线考虑因素
- 硬性期限（合同承诺、事件、合规日期）
- 对其他团队的工作或版本的依赖
- 如果该功能对于一个版本来说太大，建议分阶段进行

## 用户故事写作

好的用户故事是：
- **独立**：可以自行开发和交付
- **可协商**：细节可以讨论，故事不是合同
- **有价值**：为用户（不仅仅是团队）提供价值
- **可估计**：团队可以粗略估计工作量
- **小**：可以在一次冲刺/迭代中完成
- **可测试**：有一个明确的方法来验证它的工作原理

### 用户故事中的常见错误
- 太模糊了：“作为用户，我希望产品更快”——具体什么应该更快？
- 解决方案规定：“作为用户，我想要一个下拉菜单”——描述需求，而不是 UI 小部件
- 没有好处：“作为用户，我想点击一个按钮”——为什么？它有什么作用？
- 太大：“作为用户，我想管理我的团队”——将其分解为特定的功能
- 内部焦点：“作为工程团队，我们想要重构数据库”——这是一项任务，而不是用户故事

## 需求分类

### 莫斯科框架
- **必须具备**：没有这些，该功能就无法实现。没有商量的余地。
- **应该有**：对于启动来说很重要但不是关键。高优先级快速紧随其后。
- **可以有**：如果时间允许的话最好。如果被切断也不会延迟交货。
- **不会（这次）**：明显超出范围。可能会在未来版本中重新访问。

### 分类技巧
- 对 P0 保持无情。必备清单越紧，您发布和学习的速度就越快。
- 如果一切都是P0，那么什么都不是P0。挑战每一个必备条件：“没有这个我们真的不会发货吗？”
- P1 应该是您有信心很快就会构建的东西，而不是愿望清单。
- P2 是架构保险——它们指导设计决策，即使您现在不构建它们。

## 成功指标定义

### 领先指标
发布后快速变化的指标（几天到几周）：
- **采用率**：尝试该功能的合格用户百分比
- **激活率**：完成核心操作的用户百分比
- **任务完成率**：成功完成目标的用户百分比
- **完成时间**：核心工作流程需要多长时间
- **错误率**：用户遇到错误或死胡同的频率
- **功能使用频率**：用户返回使用该功能的频率

### 滞后指标
需要时间制定的指标（几周到几个月）：
- **保留影响**：此功能是否可以提高用户保留率？
- **收入影响**：这是否会推动升级、扩张或新收入？
- **NPS/满意度变化**：这是否改善了用户对产品的感觉？
- **支持票减少**：这会减少支持负载吗？
- **有竞争力的获胜率**：这是否有助于赢得更多交易？

### 设定目标
- 目标应该具体：“30 天内采用率达到 50%”而不是“高采用率”
- 基于可比特征、行业基准或明确假设的目标
- 设定“成功”阈值和“延伸”目标
- 定义测量方法：什么工具、什么查询、什么时间窗口
- 指定评估时间：发布后 1 周、1 个月、1 个季度

## 验收标准

以“Given/When/Then”格式或清单形式编写验收标准：

**给定/何时/然后**：
- 给定[前提或上下文]
- 当[用户采取的操作]
- 那么【预期结果】

示例：
- 鉴于管理员已为其组织配置 SSO
- 当团队成员访问登录页面时
- 然后它们会自动重定向到组织的 SSO 提供商

**清单格式**：
- [ ] 管理员可以在组织设置中输入 SSO 提供商 URL
- [ ] 团队成员在登录页面上看到“使用 SSO 登录”按钮
- [ ] SSO 登录会创建一个新帐户（如果帐户不存在）
- [ ] 如果电子邮件匹配，SSO 登录链接到现有帐户
- [ ] 失败的 SSO 尝试会显示明确的错误消息

### 验收标准提示
- 涵盖快乐路径、错误情况和边缘情况
- 具体说明预期行为，而不是实现
- 包括不应该发生的事情（负面测试用例）
- 每个标准都应该是可独立测试的
- 避免模棱两可的词语：“快速”、“用户友好”、“直观”——具体定义它们的含义

## 范围管理

### 认识范围蔓延
范围蔓延发生在以下情况：
- 规范获得批准后，要求不断添加
- “小”添加累积成一个更大的项目
- 该团队正在构建用户不需要的功能（“当我们这样做时......”）
- 发布日期不断变化，但没有明确重新调整范围
- 利益相关者添加需求而不删除任何内容

### 防止范围蔓延
- 在每个规范中写下明确的非目标
- 要求任何范围添加都必须伴随范围删除或时间线扩展
- 在规范中明确区分“v1”和“v2”
- 根据最初的问题陈述审查规范——一切都服务于它吗？
- 时间范围调查：“如果我们无法在 2 天内找出 X，我们就会削减它”
- 为不在范围内的好想法创建一个“停车场”

## 输出格式

使用具有清晰标题的 Markdown。保持文档可扫描 - 忙碌的利益相关者应该能够仅阅读标题和粗体文本来了解要点。

## 温馨提示

- 对范围有自己的看法。拥有一个严格的、定义明确的规范比一个宽泛的、模糊的规范要好。
- 如果用户的想法对于一个规范来说太大，建议将其分成几个阶段并规范第一阶段。
- 成功指标应该是具体的、可衡量的，而不是模糊的（“改善用户体验”）。
- 非目标与目标一样重要。它们可以防止实施过程中的范围蔓延。
- 开放式问题应该是真正开放式的——不要包括你可以从上下文中回答的问题。
